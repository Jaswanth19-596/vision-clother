# Stylist Intelligence Engine (2026-07-10)

Extends, does not supersede, the "LLM-as-Recommender Reversal" in `resolved-v1.md` — the LLM remains the primary recommender over a bounded text catalog, with `Domain/OutfitRecommendationValidator.swift` and `Domain/OutfitRecommendationEngine.swift` as the deterministic trust boundary and permanent offline fallback.

## Why

The recommendation pipeline works, but the knowledge driving it lived entirely as unversioned prose strings in `Domain/StylistBrain.swift`, duplicated conceptually against the numeric rules in `Domain/PairCompatibilityScoring.swift` with nothing keeping the two in sync. Separately, the LLM path passed `constraints: nil` to the validator, so dress-code (formality) alignment was only ever prompt guidance, never a deterministic check — and the learned taste profile injected into the prompt was positives-only, discarding every disliked attribute the feedback system had already computed.

## Decisions (Phase 1 — implemented)

- **Decision Hierarchy is lexicographic, not blended.** `StylistBrain.DecisionHierarchy` tiers now declare an `enforcement` (`.reject`, `.penalize`, or `.guide`). A lower tier always dominates a higher one — a beautiful outfit that breaks the dress code is wrong, not low-scoring. Only the lowest tier (aesthetic trend) is `.guide`: prompt-only, tie-breaking, never able to override a rejected/penalized tier.
- **Shared constants table, not duplicated literals.** `Domain/FashionKnowledgeConstants.swift` holds the formality-mismatch thresholds that both `StylistBrain`'s prompt prose and `PairCompatibilityScoring.aestheticPrior`'s scoring now read from — one number, two projections, verified by `StylistBrainTests`'s cross-projection consistency test.
- **Resolved constraints are self-reported, not re-extracted.** `OutfitRecommendationResponse` gained an optional top-level `resolvedConstraints: StyleConstraints` field. The recommendation prompt now asks the model to report what it resolved the scenario's dress code/weather/season to be *in the same call* that picks items — not a second call to `IntentExtractionService`, which must stay off the AI happy path (an existing tested invariant: `DailyAssistantViewModelTests.happyPathUsesRecommendationServiceAndSkipsTheFallbackEngine` asserts `intentService.callCount == 0`). `DailyAssistantViewModel` threads `response.resolvedConstraints` into the validator, so Tier 1 formality alignment is finally enforced on the LLM path.
- **Taste injection is symmetric.** `StylistBrain`'s prompt previously surfaced only attributes with affinity > 0.6 ("prioritize these"). It now also surfaces affinity < 0.4 ("tends to dislike") — the strongest personalization signal the feedback system computes, previously discarded before it ever reached the model.
- **Rejections carry a reason.** `OutfitRecommendationValidator.validateVerbose(...)` returns a `RejectionReason` (`.unknownID`, `.wrongSlot`, `.duplicateID`, `.ghostElement`) per dropped pick, additive alongside the unchanged `validate(...)`. Not wired to telemetry yet — it exists so a future "why did the LLM path yield nothing" investigation has data instead of a silent `compactMap`.
- **Fashion Constitution honesty clause.** The prompt now explicitly tells the model to say so when the wardrobe genuinely lacks a suitable item, rather than forcing a poor match, and to use respectful, non-judgmental body/appearance language.

## Decisions (Phase 1 addendum — dimension-based outfit feedback, 2026-07-10)

Replaces the outfit-level "Rate this outfit" flow's blended Fit/Comfort/Confidence/Wear-again form with dimension-based questions, each mapped to a specific part of the recommendation engine rather than one generic satisfaction score:

- **`OutfitFeedback` is a clean-break redesign, not additive.** No shipped users existed on the old shape, so `Models/FeedbackEvent.swift` replaces the outfit-level directional `fit`/`comfort`/`confidence`/`wearAgain: Bool` fields outright with Level 1 (Overall Satisfaction, Wear Again as `WearAgainAnswer` yes/maybe/no, Confidence, Comfort) and Level 2 (Occasion Match, Personal Style Match, Color Harmony, Fit & Silhouette, Weather Suitability, Practicality) plus a Favorite/Weakest Item pick — all still optional, `nil` for the simple auto-recorded "liked" write path. Item-level `ItemRating`/`FitRating` are unchanged (a future phase).
- **Every Level 2 dimension is wired to a specific affinity, not captured-and-deferred.** `Domain/AttributePreferenceProfile.swift` gained three new Bayesian-shrunk affinity maps — `styleTagAffinity` (Personal Style Match, keyed by `WardrobeItem.styleTags`), `silhouetteAffinity` (Fit & Silhouette, keyed by `WardrobeItem.silhouette`), `fabricWeightAffinity` (Weather Suitability averaged with Practicality — both describe "does this garment work for the conditions," folded into one bucket rather than inventing an 8th dimension with no scoring hook). Color Harmony and Occasion Match fold into the existing `colorVibeAffinity`/`formalityAffinity` maps alongside `ItemRating`'s contribution. All six affinities feed `affinityBonus(for:)` (now averaged over 6 dimensions, was 3) and `StylistBrain`'s symmetric taste-injection prompt block, identically to the existing color/pattern/formality treatment. *(Superseded 2026-07-24 — the engine now learns 10 dimensions, `affinityBonus` averages over 10; see the "Unified Preference Engine" addendum below.)*
- **Favorite/Weakest Item reuses the existing item-preference channel.** No new scoring math — `WardrobeRepository.fetchFeedbackHistory()` folds a favorite pick as an extra like and a weakest pick as an extra dislike into the same `itemFeedback` counts `PairCompatibilityScoring.itemPreference` already reads.
- **`SavedCombination` now persists all 4 slots.** Previously only `topItemID`/`bottomItemID` were durable, even though Daily Assistant's in-memory `OutfitCombination` always resolves footwear (and optionally outerwear). Added `footwearItemID`/`outerwearItemID` (+ denormalized labels), populated by `DailyAssistantViewModel.saveCombination()`; `nil` for Manual Pairing saves, which only ever select a top+bottom. This is what lets the Favorite/Weakest Item picker offer every real slot in the outfit.
- **Not wired this phase (deferred):** the "What would you change?" checklist (Level 3), the item-level rating overhaul (Versatility/Frequency/Style Identity/Quality Perception/etc.), and the explicit accept/edit/reject preference-confirmation card — see Deferred below.

## Decisions (Phase 1 addendum — prompt architecture restructure + accent-slot formality fix, 2026-07-14)

Two problems drove this pass: an "interview" recommendation surfaced a bag (accent items were never held to the Dress Code tier's formality bar), and independent review found the ~230-line prompt mixed policy with data and read as a step-by-step chain-of-thought script rather than a set of outcome requirements.

- **Decision Hierarchy compressed from 7 tiers to 6.** Color Harmony and Fit/Silhouette merge into one `.visualCohesion` tier — both were already `.penalize`-enforced with no behavioral distinction, so merging lets the prompt trade color vs. proportion against each other within one tier instead of rigidly ordering one over the other. Each tier's prose is now compressed into a Purpose/Priority/Never form rather than a paragraph.
- **Dress Code (Tier 2) now explicitly gates accent slots.** Previously the only accent-slot guidance was a coarse "errands/travel/work suggests bag" heuristic with no formality check on the specific item chosen — an interview scenario would loosely match "work," flag `bag` as desired, and pick any bag regardless of formality. The tier's prose now states the formality-mismatch check applies to every populated slot including accents, gives scenario-specific accent guidance (business/interview/formal → at most one subtle accessory, never headwear, bag only if a structured/formal option exists; outdoor/casual → headwear; errands/commute/travel → bag), and instructs the model to omit an accent slot rather than force a mismatch.
- **Explicit step-by-step "Reasoning Workflow" removed.** Replaced with one declarative sentence ("confirm every higher-priority tier is satisfied before considering a lower one") — modern models don't need an explicit chain-of-thought script, and the individual facts that script conveyed (resolved-constraints reporting, rationale length, confidence) moved to a plain OUTPUT FORMAT section.
- **Preferences (Tier 4) split into intrinsic profile vs. learned behavior**, and ratings are now explicitly scoped: "ratings only break ties among otherwise comparable candidates — never let a high rating substitute for correct formality, color, or fit."
- **`rationale.confidence` given real meaning.** The field already existed in the wire schema (`StructuredRationaleWire.confidence: Int`) and was fully plumbed through decode/validate, but was never explained to the model or bounded in the JSON schema. The prompt now specifies a calibrated 0-100 scale (lower when a tier required a compromise or the scenario was ambiguous), and `Services/OutfitRecommendationService.swift`'s schema gained `"minimum": 0, "maximum": 100` on that property.
- **Schema-level fix for the accent-slot bias, not just prompt prose.** `outfitRecommendationJSONSchema` uses `strict: true`, which forces every property — including the four semantically-optional accent/layer slots — into `required`; strict JSON Schema has no concept of "required key, optional value." That structural fact biases smaller models toward filling every accent slot with a plausible item just because its key is present (this is what put a formality-matching bag into an interview outfit even with the prompt's Tier 2 guidance in place). `itemIDSchemaProperties` (now `schemaProperty(for:)`) gives each optional slot's JSON Schema entry an explicit `description` separating "the key must exist" from "the value should usually be null," with slot-specific guidance (`bag_id`'s calls out interview/formal-business by name) — this is a second, schema-level backstop alongside the prompt-prose fix, since the prompt alone wasn't sufficient against strict mode's required-key bias.
- **New diversity and ranking objectives.** Outfits must differ by at least one primary garment or a clearly different styling direction (no near-duplicate color swaps), and `outfits` must be sorted strongest-to-weakest so index 0 is always the best recommendation.
- **Validator/architecture jargon removed from the prompt.** The `resolved_constraints` instruction no longer mentions "the on-device validator" — the model doesn't benefit from knowing the software architecture, only what it must populate and why it must be truthful.
- Not touched this pass: `OutfitRecommendationEngine`, `OutfitRecommendationValidator`, `Domain/FashionKnowledgeConstants.swift`, and multi-accessory support (letting an outfit hold several simultaneous accessories) — the latter requires a schema/engine/validator/SwiftData migration across ~12 files and is scoped as a separate future phase.

## Decisions (Item Rating question redesign + Swipe-to-Learn implicit swipe bridge, 2026-07-15)

User feedback on the per-item rating form (`Features/Rating/RateItemView.swift`): the questions read as generic and out of scope. Tracing the scoring path confirmed the deeper cause — every answer (Fit, Comfort, Confidence, Wear-again, Versatility, Predicted Wear Frequency, Style Identity, Quality Perception) was averaged into one blended `ItemRating.normalizedValue`, and that single number was reused as the signal for three unrelated affinities (color, pattern, formality) with no dedicated color or pattern question ever asked. Versatility/Frequency/Quality Perception fed nothing else — they only diluted the blend.

- **Question set redesigned to map 1:1 onto scoring dimensions.** `Models/ItemRating.swift` replaces Confidence/Versatility/Frequency/Quality Perception with `colorLike` ("do you like this color on you?"), `patternLike` (optional — the Pattern question is skipped for solid-pattern items), and `formalityFit` ("did this feel right for how formal/casual you needed it?"). Fit, Comfort, Style Identity, and Wear Again are unchanged. Clean-break schema change (no shipped users), matching the precedent set by the `OutfitFeedback` redesign above.
- **`RatedAttributes` (`Domain/AttributePreferenceProfile.swift`) carries dedicated per-attribute fields instead of one blended `value`.** `colorLike` feeds `colorVibeAffinity`, `patternLike` feeds `patternAffinity` (skipped when `nil`), `formalityFit` feeds `formalityAffinity`, `styleIdentity` still feeds `styleTagAffinity` (unchanged). Two attributes that previously had no item-level signal at all now do: `fit.centeredness` feeds `silhouetteAffinity` when the item has a `silhouette` tag, and `comfort` feeds `fabricWeightAffinity` — both alongside the existing outfit-level `Fit & Silhouette`/`Weather Suitability`+`Practicality` contributions.
- **Item ratings now close the loop into Swipe-to-Learn Visual Taste.** A highly-rated item (`ItemRating.impliesLiked`, the existing `>=0.6` threshold) is treated as an implicit "swipe right" on its cached photo embedding; a poorly-rated one as an implicit "swipe left" — nudging the same `VisualPreferenceState` centroids `Features/SwipeDiscovery/` writes (`Data/WardrobeRepository.swift`'s new `applyImplicitSwipe`, called from `recordItemRating`). This keeps the k-means visual profile learning from real wear history even after a user stops swiping the discovery deck, and keeps the text-attribute profile and the visual embedding space in sync from the same feedback moment.
- **Implicit swipes use a gentler, fixed learning rate than explicit swipes.** `VisualClusterUpdater.update` gained an optional `learningRate: Float?` parameter (`nil` preserves the existing `1/weight` incremental-mean step used by every pre-existing call site). `VisualClusterUpdater.implicitLearningRate = 0.05` is used only for rating-derived updates — a rating is a more passive, ambient signal than a deliberate swipe gesture and arrives far more often, so it should move the centroids less per event.
- **Implicit swipes are best-effort and don't write a `SwipeEvent`.** `applyImplicitSwipe` no-ops (silently, via `try?` at the `recordItemRating` call site) if the item has no cached `WardrobeItemEmbedding` yet — embeddings are computed lazily by `fetchFeedbackHistory()`, so a rating recorded before that happens simply misses one nudge rather than blocking the rating save on an async Vision computation. It also doesn't insert a `SwipeEvent`: a rating isn't a discrete stock-photo swipe, so `VisualPreferenceProfile.build(from:dislikedEmbeddings:)`'s history-replay recovery path stays scoped to actual swipe gestures.
- **`dislikePenaltyWeight = 1.2` and `maxBonusMagnitude = 0.3` in `Domain/VisualPreferenceProfile.swift` are unchanged** — this pass only adds a new writer into the existing centroid/scoring pipeline, not a new formula.

## Decisions (Calibration meter + `[AI-Stylist-ML]` verification logging, 2026-07-15)

A follow-up request asked for the swipe-deck's Vision-embedding/k-means pipeline to be built essentially from scratch, with a specific formula/parameter spec. Investigation found the entire pipeline already shipped (the two decisions above) — Pexels query pool, `VisualClusterUpdater`'s k-means, the catalog-truncation and re-scoring integrations all already matched the spec's numbers almost exactly (`dislikePenaltyWeight = 1.2`, `maxBonusMagnitude = 0.3`, `implicitLearningRate = 0.05`). Two spec details did *not* match already-shipped, documented behavior — nearest-centroid assignment via Euclidean distance (existing: cosine similarity, so downstream scoring stays a plain dot product) and a fixed η=0.10 explicit-swipe step (existing: `1/weight` incremental mean, which already decays the step size as a centroid matures). Confirmed with the user to **keep the existing math unchanged** rather than rewrite tested/documented behavior to match the letter of a spec that was, in effect, redescribing what already shipped. What was genuinely missing — a persisted calibration/training signal and `[AI-Stylist-ML]`-tagged diagnostic logging — was added on top:

- **`VisualClusterUpdater.update` now returns the nudge's drift percentage** (`‖c_new - c_old‖ * 100`, both sides unit-length) — `nil` when the call seeded a fresh centroid or hit the dimension-mismatch reseed path (no prior vector to diff against). Pure, no logging inside `Domain/VisualPreferenceProfile.swift` itself — callers log it.
- **`VisualPreferenceState` (`Models/SwipeDiscovery.swift`) gained `totalSwipes: Int`**, incremented only by `recordSwipe` (explicit deck swipes) — not by `applyImplicitSwipe`'s rating-derived nudges, which stay an ambient, gentler signal per the entry above, not a calibration action. Two computed properties: `calibrationProgress: Double` (linear `totalSwipes / 20`, capped at 1.0) and `isTrained: Bool` (`calibrationProgress >= 1.0`). Deliberately **not** gated on a `consecutiveStableUpdates`/"stability" dimension — the spec named such a field but never defined what "stable" meant, and the user's follow-up direction dropped it in favor of this simpler, purely swipe-count-driven meter.
- **`[AI-Stylist-ML]`-tagged logging**, added at three points per the request: (1) `Data/WardrobeRepository.swift`'s `recordSwipe`/`applyImplicitSwipe` log the drift percentage on every swipe (tagged `type=explicit`/`type=implicit`); (2) `recordSwipe` logs once when `isTrained` flips false→true; (3) `Domain/WardrobeCatalogBuilder.swift`'s `rank(_:history:)` logs each item's computed visual affinity bonus while ranking a slot, gated on the profile actually having centroids (a cold-start profile scoring everything 0 would just be log noise). New `Domain/MLLog.swift` holds the shared `Logger` — kept in `Domain/` rather than reusing `Services/PerfLog.swift` so `WardrobeCatalogBuilder` (Domain) doesn't need a `Services/` import (Domain/CLAUDE.md); `WardrobeRepository` (Data) reuses the same logger instance since it already depends on `Domain/` types here.
- **Calibration is surfaced in the UI as a gamified ring, not a raw log readout.** `Features/SwipeDiscovery/CalibrationRingView.swift` (new) is an Activity-ring-style meter — `CalibrationRingView` (the ring itself, spring-animated fill, checkmark at 100%) and `CalibrationProgressBadge` (ring + "Stylist Calibration" label, wrapped in `.premiumCard()`) — mounted at the top of `SwipeDiscoveryView`. `SwipeDiscoveryViewModel` exposes `calibrationProgress`/`isTrained`, refreshed via a best-effort `fetchVisualPreferenceState()` read on deck load and after every persisted swipe.
- **Vector math stays pure Swift, not Accelerate/vDSP.** Confirmed with the user — the existing `l2Normalized`/`cosineSimilarity` loops are already NaN-safe and tested, and 768-dimension vectors are cheap enough that a vDSP rewrite wasn't worth the diff against tested behavior for this pass.

## Decisions ("What Would You Change?" Checklist — Level 3, 2026-07-15)

Closes the second of three items tracked in this file's Deferred section: the Phase 1 addendum shipped Level 1/2 dimension-based outfit feedback but stopped short of "the 'What would you change?' checklist (Level 3)." No prior spec existed anywhere in the repo/docs for what the checklist's actual options should be — the seven below were defined fresh, each mapped 1:1 onto an existing (or newly-fed) affinity dimension, following this file's own stated design philosophy ("every dimension wired to a specific affinity, not captured-and-deferred").

- **Seven checklist options, six dimensions.** `Models/FeedbackEvent.swift`'s new `OutfitChangeReason` enum: Too Formal / Too Casual → `formalityAffinity` (mutually exclusive — selecting one clears the other, `RateCombinationViewModel.toggleChangeReason`), Wrong Colors → `colorVibeAffinity`, Wrong Pattern → `patternAffinity`, Not My Style → `styleTagAffinity`, Didn't Fit Right → `silhouetteAffinity`, Wrong For The Weather → `fabricWeightAffinity`.
- **"Wrong Pattern" is the first outfit-level entry point into `patternAffinity`.** Every other dimension already had an outfit-level Level 2 star question feeding it; pattern didn't (only item-level `ItemRating.patternLike` fed that map). `Domain/AttributePreferenceProfile.swift`'s `OutfitDimensionRatedAttributes` gained `pattern: GarmentPattern` (the item's actual pattern) and `patternDissatisfaction: Double?` (`nil` unless flagged), folded into `patternSums` in `build(from:outfitDimensionRatings:...)` identically in shape to the other five dimensions.
- **A flagged reason clamps, it doesn't replace.** `Data/WardrobeRepository.swift.fetchFeedbackHistory()`'s per-item `OutfitDimensionRatedAttributes` construction applies `min(existingNormalizedValue, 0.1)` for every flagged reason's dimension — so a user who gives a high Color Harmony star but also flags "Wrong colors" (e.g. rating charitably overall while still pointing at one specific miss) still contributes a strongly negative `colorVibeAffinity` signal, rather than the checklist being purely redundant with a low star.
- **No new scoring primitive.** The clamp reuses the exact same accumulation/shrinkage pipeline every other dimension already goes through (`AttributePreferenceProfile.build`) — this was a deliberate constraint per this file's design philosophy, not an oversight.
- **UI**: `Features/Rating/RateCombinationView.swift` gained a "What Would You Change?" `Form` section (`ChangeReasonChecklist`, a plain multi-select list of toggleable rows) between the Level 2 questions and the Favorite/Weakest picker.
- **`SchemaV7`** (`Models/SchemaMigrations.swift`) — `OutfitFeedback.changeReasonsRaw: [String] = []`, purely additive, `.lightweight` migration; `SchemaV6.OutfitFeedback` gained the frozen pre-`changeReasonsRaw` nested snapshot this requires.

## Decisions (Multi-Accessory Outfits, 2026-07-15)

Closes the last of three items tracked in this file's Deferred section — "multi-accessory support (letting an outfit hold several simultaneous accessories)" was explicitly scoped out of the 2026-07-14 prompt-restructure pass as needing "a schema/engine/validator/SwiftData migration across ~12 files."

- **Investigation found the gap narrower than "one accessory total."** Cross-slot accessorizing already worked — `Slot` already has three independent accent cases (`headwear`, `accessory`, `bag`), each 0-1. The actual constraint was that `.accessory` is an explicit catch-all bucket ("belt, scarf, tie, watch, or sunglasses... one per outfit, not several simultaneously," per `StylistBrain.swift`/`OutfitRecommendationService.swift`'s prior prose) — so a request like "bag + belt + jewelry" collided only on the belt/jewelry pair sharing one slot; the bag was always fine.
- **Fix is additive, not a redesign.** The primary `.accessory` slot (and every other slot's `[Slot: WardrobeItem]` dictionary shape) is untouched — zero risk to existing behavior or test coverage. A bounded **supplementary accessories** list (`FashionKnowledgeConstants.DressCode.maxSupplementaryAccessories = 2`) was added as a wholly separate field at every layer: wire (`RecommendedOutfitWire.supplementaryAccessoryIDs`, decoded through the existing dynamic-key `Codable` container under a fixed `supplementary_accessory_ids` key), JSON schema (a capped array property — an empty array natively expresses "nothing extra," no required-but-nullable hack needed the way scalar optional slots require), validator (`OutfitCombination.supplementaryAccessories`), persistence (`SavedCombination.supplementaryAccessoryItemIDs`/`Labels`, new `SchemaV8`), prompt (`StylistBrain`), and UI (`OutfitCardView`).
- **The validator's existing per-slot `Slot.allCases` loop is untouched** — supplementary accessories are resolved as one explicit extra step alongside it, not woven into it, per `Domain/CLAUDE.md`'s guardrail against ad hoc per-slot special-casing inside that generic loop. The duplicate-id check was extended to cover supplementary ids too (can't repeat the primary accessory or each other).
- **Over-cap supplementary ids are truncated, not rejected.** The schema's `maxItems` should prevent this from the model side, but the validator defensively takes only the first `maxSupplementaryAccessories` rather than hard-failing the whole outfit over a minor schema violation.
- **Scenario-gated in the prompt, same tier as the existing single-accessory rule.** Business/interview/formal-event scenarios must leave `supplementary_accessory_ids` empty (same ceiling as the existing "at most one subtle accessory" rule); only casual/going-out scenarios may use up to the cap.
- **`Features/JobQueue/JobQueueStore.saveCombination`** and **`Features/Combinations/CombinationsViewModel.resolveItems(for:)`** are the two integration points that build/resolve a `SavedCombination` from/to real items — both updated to carry the new fields; Manual Pairing saves (top+bottom only) are unaffected since they never populate `supplementaryAccessories`.

## Decisions (Impression/Selection Event Capture, 2026-07-15)

Closes one of three deferred items below (multi-accessory outfits and the Level 3 feedback checklist are tracked separately as they land). The app already logged ML drift (`[AI-Stylist-ML]`) but never recorded which of several shown candidate outfits the user actually acted on vs. ignored.

- **New event-sourced `Models/RecommendationImpressionEvent.swift`**, mirroring `SwipeEvent`'s shape rather than `FeedbackEvent.swift`'s tables — there's no durable `SavedCombination.id` to key against at impression time, since an ignored candidate is never persisted. One row is inserted per candidate the moment `DailyAssistantViewModel.sendTurn` resolves a successful round, keyed by the in-memory `OutfitCombination.id` (stable for the lifetime of that value within the round) with `rank` = its position in the LLM's already-strongest-to-weakest sort.
- **`startTryOn` is the "selection" gesture.** Among the concrete "pick" actions in the app, tapping "How does it look on me?" is the one that corresponds to choosing one candidate over its shown siblings — `DailyAssistantViewModel.startTryOn` marks that impression row's `selectedAt`. The later save/like flow (`JobQueueStore.saveCombination`) is decoupled from round context entirely and untouched by this change.
- **Both new repository methods (`recordImpressions`/`recordSelection`) are best-effort**, called via `try?` exactly like `applyImplicitSwipe` — a logging/audit trail, never a gate on the conversation flow — and log under the existing `[AI-Stylist-ML]` tag (`Domain/MLLog.swift`).
- **Not wired into any ranker this phase** — same posture as `OutfitRecommendationValidator.RejectionReason`: the data now exists so a future "which of our recommendations actually land" investigation has something to query, but `AttributePreferenceProfile`/`PairCompatibilityScoring` don't read it yet.

## Decisions (Unified Preference Engine — one taste model, 2026-07-24)

Collapses the two parallel taste engines into one and widens what it learns, so a single `AttributePreferenceProfile` drives recommendations, Insights *and* shopping.

- **The pixel/embedding engine is retired.** `VisualPreferenceProfile` (k-means over `VNGenerateImageFeaturePrint` embeddings) previously contributed a `meanVisualBonus` re-rank term to `OutfitRecommendationEngine.outfitScore` and a tie-break in `WardrobeCatalogBuilder.rank`, but never appeared in Insights and duplicated a signal the attribute engine already captured better. Both consumers now read `AttributePreferenceProfile` (`FeedbackHistory.visualProfile`/`itemEmbeddings` and the per-item embedding pass in `fetchFeedbackHistory` were deleted; `applyImplicitSwipe` too). `SwipeEvent`/`VisualPreferenceState`/`WardrobeItemEmbedding`/`VisualPreferenceProfile`/`VisualClusterUpdater` remain as inert types to avoid a destructive SwiftData migration; only `VisualPreferenceState.totalSwipes` survives, bumped by `WardrobeRepository.noteSwipeForCalibration` to drive the swipe deck's calibration ring.
- **Dead code deleted (2026-07-27).** The 2026-07-24 pass left the retired engine's *code* in the tree, unreferenced. It has now been removed: `Domain/VisualPreferenceProfile.swift` (incl. `VisualClusterUpdater`), `Services/ImageEmbeddingService.swift`, `Services/WardrobeEmbeddingWorker.swift`, the repository's `recordSwipe`/`updateVisualPreferenceState`/`fetchWardrobeItemEmbedding`/`saveWardrobeItemEmbedding`, `SwiftDataWardrobeRepository`'s `embeddingService` init parameter, `ServiceFactory.makeImageEmbeddingService`, `VisualCentroidDTO` and the centroid fields on `VisualPreferenceStateDTO`, and the dead `DriftFeedbackPill` view. What deliberately stays: the `@Model` types `SwipeEvent`/`WardrobeItemEmbedding` and `VisualPreferenceState`'s three centroid columns, as inert storage. Dropping a stored property or model from a `@Model` changes the SwiftData schema hash, so reclaiming them needs a `SchemaV19` *plus* a frozen nested snapshot in every prior version that shares the current shape (V5-V18, per the `SchemaV4.VisualPreferenceState` precedent) — disproportionate migration risk for two unread tables and three unread columns on a single row.
- **Four new learned dimensions.** `AttributePreferenceProfile` gained `undertoneAffinity`, `materialAffinity`, `textureAffinity`, `fitAffinity` — the vision LLM already extracted these per garment (`GarmentMetadata`) but they were dropped. They come from both swipes (`SwipeAttributeEvent` gained the four columns, `SchemaV14`, at full strength) and owned-item ratings (reusing existing answers as each one's signal: undertone←`colorLike`, material/texture←`comfort`, fit←`fit.centeredness`; outfit-dimension feedback reuses Color Harmony / Weather+Practicality / Fit & Silhouette). `affinityBonus`/`matchDetail` now average over **10** dimensions (each unrated attribute still contributes a neutral 0.5, so the bonus stays byte-compatible at cold start), and `StylistBrain`'s symmetric injection surfaces Undertones/Materials/Textures/Fits alongside the original six. **Seasonality is deliberately not learned as taste** — it's weather/context (already consumed by the weather penalty), not a preference.
- **Insights reflect the merged profile.** `StyleDNAScorer` added Material Signature + Texture Preference (14 dimensions total); "Test Your Style" surfaces the new `matchDetail` components automatically. Because swipes already fold into `AttributePreferenceProfile`, every Insights surface (Colors, Style DNA) now reflects swipe taste too — previously the swipe/pixel signal never reached Insights at all.
- **Shopping is taste-aware.** `Domain/ClosetGapAnalyzer.swift` and `Domain/ShoppingInsightsAggregator.swift` take the `attributeProfile` (fed by `WardrobeInsightsViewModel` via the version-cached `fetchFeedbackHistory`) and steer structural gaps' `targetColorVibe`/descriptions toward the user's strongest learned color vibe/material, plus a new "Preferred Style Underrepresented" gap — grounding "buy the best items to improve your style" in the user's own demonstrated taste rather than pure count-based balance. Both fall back to their original taste-free phrasing at cold start.
- **The profile has an explicit user-facing surface (Insights → "Taste", 2026-07-24).** `Domain/TasteInsightsAggregator.swift` is the read-side presentation of the unified profile: it re-expresses the 10 flat affinity maps as ranked, human-labeled rows per dimension plus `loved`/`avoided` splits (reusing the same > 0.6 / < 0.4 thresholds `StylistBrain`'s injection uses, so what the user sees matches what the recommender is told) and a one-line "fingerprint". It gates on `hasSignal` and drops neutral-only dimensions so a cold-start user sees a "still learning" prompt, not a flat all-50% chart. The formerly-empty "Discover" Insights tab became **"Taste"** (`TasteInsightsView`, ranked bars via the shared `RankedBarShareChart`); a compact `TasteCalloutCard` (fingerprint + top loved chips) now also anchors the Overview, Trends, and Wardrobe tabs so the whole Insights surface reflects the user, not just their closet. Style is unchanged (its DNA radar already surfaced taste). This is presentation-only — no engine/schema change.

## Decisions (Multi-Garment "Discover Your Style" + 4-Point Sentiment + Chemistry Insights, 2026-07-26)

Widens the swipe deck from a flat binary/single-garment signal to a richer, more accurate one, and surfaces a genuinely new whole-look signal in Insights.

- **Every visible worn garment is tagged, not just one "hero" piece.** `Services/VisionMetadataExtractionService.swift`'s `extractSceneMetadata(imageData:)` replaces the `.wornInScene` `GarmentExtractionFocus` case — a single-garment photo still yields one tagged garment, but a full-outfit photo now yields the complete set (top/bottom/footwear/outerwear/accessories) instead of discarding everything but the primary piece. `Models/SwipeDiscovery.swift`'s `SwipeAttributeEvent` is accordingly now keyed `(sourcePhotoID, slot)` rather than `sourcePhotoID` alone, so one swiped photo can produce multiple rows.
- **Sentiment is a 4-point scale, not binary.** `SwipeSentiment` (love/like/dislike/hate) maps to `ratingValue` 1.0/0.75/0.25/0.0 — symmetric around the engine's existing neutral 0.5, so love/hate are simply a stronger version of the same signal like/dislike already taught, not a new axis. Input is distance-based drag (a second, larger `SwipeGestureResolver.intenseThreshold` past the existing commit threshold) plus a 4-button fallback row; UI feedback scales with intensity (bigger stamp/stroke, `.impact(weight: .heavy)` vs. `.light)` haptic) but the *learning* stays exactly as invisible as before — no "here's what we learned" reveal.
- **Legacy binary swipes migrate to the moderate values, never the extremes.** `SchemaMigrations.swift`'s `.custom` `migrateV15toV16` stage maps a pre-migration `liked: Bool` to `.like`/`.dislike` — a past binary swipe carried no intensity signal, so it would be wrong to backfill it as a `.love`/`.hate` the user never actually expressed.
- **Whole-look signal gets its own affinity dimension, deliberately isolated.** `AttributePreferenceProfile.colorHarmonyAffinity` (keyed by `ColorHarmonyDescriptor`, see `docs/domain/vision-clother-concepts.md`) is learned only from the new `SwipeCombinationEvent` table (one row per swiped photo with 2+ garments) — there's no owned-item baseline for a color-harmony *pairing*, unlike every other dimension, so it floors at the flat `PairCompatibilityScoring.defaultPriorWeight` rather than the closet-composition-scaled dynamic prior. It is **not** folded into `matchDetail(for: WardrobeItem)`/`affinityBonus` (those score one item at a time) and **not** wired into `OutfitRecommendationEngine`/`StylistBrain` scoring — Insights-only in this pass, matching the "re-rank, don't hard-filter" and "learning stays invisible" postures every other dimension in this engine already follows. `styleCoherenceTags` reuses the existing `styleTagAffinity` map instead of a parallel one, since it's the same "style identity" signal single-garment `styleTags` already teaches.
- **Chemistry gets a dedicated Insights sub-tab, not a bolt-on card.** `Domain/OutfitChemistryAggregator.swift` is the read-side presentation — ranked Color Harmony and Style Coherence bars (reusing the promoted `AffinityBarRow` component, formerly `TasteInsightsView`'s private `TasteBarRow`), a "Rule-Breaking" card (share of loved/liked swiped outfits whose `FormalityConsistency` was `.intentionalContrast`), and a "Why These Work" card (sample rationale sentences from loved combos). `Domain/InsightsSummaryBuilder.swift` (the Q&A summary) deliberately does **not** gain a Chemistry section in this pass, consistent with the existing Taste tab / "Taste vs. Closet" precedent (both shipped without being folded into that summary either) — flagged as an isolated follow-up, not an oversight.

### Correction (2026-07-27): `combination` applicability moved client-side

Shipped 2026-07-26 with `combination` modeled as a nullable *object* in the vision LLM's structured-output schema (`"type": ["object", "null"]`) — the model itself decided, per photo, whether to null the whole object out for a single-garment photo. In practice this meant **zero** `SwipeCombinationEvent` rows were ever created even after 50+ swipes of genuine full-outfit photos (the swipe deck's Pexels queries are all full-body/lookbook shots), leaving the Chemistry tab permanently stuck on its "still learning" empty state. Root cause: a nullable-*object* structured-output shape (unlike the nullable-*scalar* shape already used successfully elsewhere, e.g. `fit`/`material`) isn't reliably honored across every vision model reachable via OpenRouter, and giving the model an explicit "omit this entire object" escape hatch made it default to skipping it regardless of what was actually in the photo. Fix: `combination` is now a plain required object the model *always* fills in with its best-effort whole-look read; `VisionMetadataExtractionService.performSceneRequest` applies the real 2+-garment gate itself, client-side, from `garments.count` — a value it can check deterministically rather than trusting the model to null a whole object correctly. No change to any downstream consumer (`WardrobeRepository`, `AttributePreferenceProfile`, `OutfitChemistryAggregator` all already branched on `sceneMetadata.combination != nil`).

## Decisions (AI Stylist Data Model Refactor — category-partitioned taste, 1/N credit assignment, Swipe + Comment combination feedback, 2026-07-27)

Three gaps surfaced by a full codebase audit: preference profiles were almost entirely flat/global (one "loves bold patterns" number across the whole wardrobe, not per-category), a multi-garment swipe injected N× the raw signal of a single-garment swipe for the same sentiment (no 1/N credit assignment), and the only way to give feedback on a user's own assembled combination was the heavy multi-question form from the "dimension-based outfit feedback" addendum above — high-friction, and far coarser than what the vision LLM already infers automatically for stock swipe photos.

- **The Level 1/2/3 "Rate this outfit" form is retired, not extended.** `Features/Rating/RateCombinationView.swift` collapses from a two-step flow (whole-outfit dimension form → per-item follow-up rating) to a single swipe+comment screen. The per-item follow-up step is removed entirely, not just decoupled — `RateItemView.swift`/`RateItemViewModel.swift` are deleted (their sole caller was this flow; `RatingSaveState` moved to `RateCombinationViewModel.swift`, the type's new only consumer). Historical `OutfitFeedback` rows from the old form are untouched and still read by `normalizedRating`/`outfitDimensionRatings` exactly as before — this is a new write path added to the same table, not a data migration.
- **Category-partitioned taste, generalized from the existing color-only precedent.** `colorVibeAffinityBySlot` (added for the Style Analytics color chart, never used for scoring) is the template every other dimension now follows: `patternAffinityBySlot`, `formalityAffinityBySlot`, `styleTagAffinityBySlot`, `silhouetteAffinityBySlot`, `fabricWeightAffinityBySlot`, `undertoneAffinityBySlot`, `materialAffinityBySlot`, `textureAffinityBySlot`, `fitAffinityBySlot`. Unlike the color precedent, these are now actually read by scoring — `matchDetail(for:)`/`affinityBonus` call new slot-aware accessors (e.g. `colorVibeAffinity(_:slot:)`) that prefer the per-slot breakdown when the candidate's own slot has data, falling back to the flat map otherwise, so no existing caller of the flat maps needed to change.
- **1/N credit assignment, composed with decay, not replacing it.** `WardrobeRepository.recordSwipeAttributes` computes `1.0 / Double(garments.count)` once per swiped photo and stamps it onto every resulting `SwipeAttributeEvent` row (new `weight` column). `AttributePreferenceProfile.build()`'s accumulation weight becomes `decayWeight(...) * rating.weight` — a single multiplication, so recency and garment-count credit assignment compose rather than one overriding the other.
- **Swipe + Comment combination feedback reuses the Discover deck's own gesture primitive.** `Features/Rating/RateCombinationView.swift`'s new screen applies `SwipeGestureResolver` (already stateless, SwiftUI-decoupled, unit-tested) to the combination's own image instead of a card deck. `Services/CombinationChemistryInferenceService.swift` is a new **text-only** call — deliberately not a method on `VisionMetadataExtractionService` (image-in by definition) — that infers the same `CombinationMetadata` shape (see `docs/domain/vision-clother-concepts.md`'s "Whole-look color harmony" section for the original 4 fields, now 14) from the combination's own already-known `CatalogEntry` attributes plus the user's sentiment/comment. Routes through `ProxyConfig.openRouterChatURL` (uncapped), not `openRouterRecommendURL` — this is a tagging/extraction utility, not a recommendation, matching `IntentRoutingService`'s precedent for why that distinction matters cost-wise.
- **The chemistry-inference call never blocks the swipe from saving.** `RateCombinationViewModel.submit()` persists sentiment + comment synchronously first (`WardrobeRepository.recordCombinationSwipeFeedback`, `chemistry: nil`), then fires the inference call in a background `Task` that updates the same row once it resolves — a slow or failed LLM call degrades to "sentiment saved, chemistry never filled in" rather than blocking or losing the user's swipe.
- **Whole-look chemistry finally reaches recommendation scoring, ten fields deep.** The 2026-07-26 addendum above deliberately kept `colorHarmonyAffinity` Insights-only, since the recommendation LLM never sees images and can't judge whole-look chemistry for an arbitrary candidate outfit. This pass adds a **deterministic on-device estimator** instead of trying to teach the LLM to judge it: `PairCompatibilityScoring.estimateCombinationHeuristics(_:)` derives the 7 objectively-computable new combination dimensions (paletteArchetype/contrastLevel/colorSandwiching/proportionRatio/volumeBalance/textureContrast/formalityBridge) from a candidate outfit's own item attributes, reusing `ColorHarmony`'s hue math and `FashionKnowledgeConstants.DressCode`'s formality thresholds rather than inventing new math. `AttributePreferenceProfile.combinationAffinityBonus(for:)` scores that estimate against learned combination taste and folds into `OutfitRecommendationEngine.outfitScore`, cold-start-safe by construction (empty profile → empty affinity maps → bonus is exactly 0). `overallAestheticVibe`/`complexityScore` stay Insights-only, same reasoning as the original `colorHarmonyAffinity` decision — there's no reliable deterministic proxy for a whole outfit's subjective vibe or visual complexity.

## Decisions (Making the refactor visible — per-category Taste cards, learned expanded attributes, a Chemistry tab that asks, 2026-07-27b)

The refactor above shipped its data model correctly but was invisible in the app: the user reported the Insights tab looked unchanged, with no per-category breakdown anywhere and a permanently empty Chemistry tab. All three causes were surfacing gaps, not data-model bugs.

- **Category-partitioned taste needed a read side, not just a write side.** The nine new `*AffinityBySlot` maps were read by `matchDetail(for:)` and nothing else — `TasteInsightsAggregator` still consumed only the flat maps, so the Taste tab rendered exactly what it had before. Fixed on the read side alone (no change to how the maps are built or scored): `Dimension` gained `categories: [Category]`, built by a generic `makeCategories` helper shared by both the enum-keyed and string-keyed dimension builders, and `TasteInsightsView` renders it as a collapsed "By category" disclosure per card. Collapsed by default deliberately — with up to seven slots per dimension, expanding everything would bury the overall ranking that is still the headline.
- **The 5 expanded per-garment attributes were extracted, stored, and prompted — but never learned.** Adding five more affinity dimensions raised the question of whether they should dilute `matchDetail`'s previously-fixed 10-way mean. They don't, unconditionally: each joins the mean **only if the profile has learned anything for that dimension at all**. For a closet ingested before the expanded extraction every new map is empty, so the mean is still exactly the 10-way one and scoring is bit-for-bit unchanged; once items carrying these fields are rated, the dimensions start pulling their share. This is a deliberate departure from the "fixed N-way mean, unrated attributes contribute a neutral 0.5" convention the ten existing terms follow — the difference is that those ten are populated for essentially every item, whereas these five are populated for *no* item ingested before 2026-07-27, so a fixed 15-way mean would have weakened every existing user's personalization by a third in exchange for nothing.
- **The Chemistry tab's empty state now asks for the feedback it needs instead of pointing elsewhere.** Chemistry is the one Insights surface with no closet-composition fallback — it can only describe outfits the user has actually reacted to — and its predecessor empty state just told the user to go swipe in the Discover deck. That was especially poor after the two same-day `combination`-extraction fixes: a user's historical swipes are permanently un-retaggable (`recordSwipeAttributes` dedups by `sourcePhotoID`), so their existing swipe history could never fill this tab retroactively. The empty state now lists the user's own saved outfits that carry no chemistry yet and opens `RateCombinationView`'s swipe+comment flow on each directly; the same list reappears as a "Sharpen This" card below real content once signal exists. **Deliberately not done:** back-filling chemistry by running `estimateCombinationHeuristics` over already-rated saved outfits. It would have populated the tab instantly from existing data, but the same estimator is what `combinationAffinityBonus` scores candidates *with* — seeding the profile from it would make the Chemistry tab partly a readout of the app's own heuristics rather than of the user's taste, and the user chose to supply real feedback instead.

## Decisions (Item-Level Feedback + closing the learning loop — `ItemNote`, per-slot chips, the `itemSuitability` tier, combination/per-category taste in the prompt, 2026-07-27c)

A full trace of the feedback path (swipe/rating -> learned profile -> Insights -> recommendation -> "Test Your Style") found the chain intact in four places and broken in five. Worst first: the swipe+comment flow from the refactor above records a whole-look sentiment with no per-dimension answers, so its `OutfitFeedback` rows have a `nil` `normalizedRating`, are filtered out of `detailedOutfitFeedbacks`, and produce zero `outfitDimensionRatings` — rating your own outfit taught whole-look chemistry and *nothing per-garment*. Since the same refactor deleted `RateItemView` (leaving `recordItemRating` with no caller outside the repository), per-category taste learned from the user's own closet had stopped moving entirely; only stock-photo swipes still fed it. Compounding that, `AnalyticsAggregator`'s `ratingSampleSize` counted only the retired form, so Style DNA — the sole taste-derived content in `InsightsSummaryBuilder` — could never unlock from real usage, and the assistant kept answering "not enough ratings yet" to a user who had rated plenty. Separately, `StylistBrain` surfaced only the ten flat item-level affinity maps: whole-look combination taste reached recommendations *only* via `combinationAffinityBonus` re-ranking outfits the model had already chosen, the `*BySlot` maps never reached the prompt at all, and the five expanded attributes learned in the pass above were absent from it.

- **A garment defect is not a taste preference, and the two get different storage.** "This shirt is loose" and "I don't like this colour on me" are the same gesture with opposite consequences: the first is a fact about one garment that must never touch `fitAffinity` (the user may well love relaxed fits in general — teaching "dislikes loose" would suppress every relaxed garment they own) and must not decay; the second should generalize per-slot and decay on the usual half-life. Taste chips therefore write `ItemRating` (reused unchanged — the 2026-07-27 refactor deleted the *form*, not the schema, and `FitRating`'s two-directional scale was already exactly the axis needed); defect chips write the new `ItemNote`.
- **`ItemNote` is deliberately mutable — the one feedback table in this app that isn't event-sourced.** Every other (`ItemRating`, `OutfitFeedback`, `SwipeAttributeEvent`) is append-only because it feeds a time-decayed aggregate where history *is* the signal. A note is a current-state claim about a garment, and the user must be able to correct or remove it; modeling it append-only would require tombstones and override-event layering to express "that note was wrong", buying nothing since no decayed aggregate reads it. Accepted consequence: a deleted note leaves no trace, which is correct — deleting asserts the note was wrong, not that the garment changed. `SchemaV18` adds the entity (lightweight stage, no backfill); it syncs like any other entity (`ItemNoteDTO`, `SyncEntityType.itemNote`, `itemNotes` collection), and is the only *mutable* synced entity, so `applyItemNoteChange`'s `shouldSkipDueToLocalDirty` guard does real work rather than being kept for consistency.
- **Suppression got its own Decision Hierarchy tier, and a harder mechanism sits above it.** `ItemNoteSeverity.conditional` (the common case) is enforced by the new `DecisionHierarchy.itemSuitability` at position 3, `.penalize`, with the deterministic projection the tier contract requires: `outfitScore` penalizes an item whose note context matches the request (`formalOccasions` against the resolved formality floor, `coldWeather`/`hotWeather` against the weather, `extendedWear` always but small, `none` never), with every threshold in `FashionKnowledgeConstants.ItemSuitability` per Domain/CLAUDE.md's "never re-literal a number the prompt also names". `ItemNoteSeverity.blocking` is *not* a tier at all: the item is excluded from the catalog in `WardrobeCatalogBuilder`, exactly as the laundry filter already works — the LLM cannot pick what it never sees, so it's unbypassable and free, where a prompt rule is only as good as model compliance. **Accepted cost:** inserting a tier renumbers Weather 3->4, Preferences 4->5, Visual Cohesion 5->6, Aesthetic Trend 6->7 throughout prompt text the current model behavior was tuned against. Not avoidable while honoring "suppression gets its own tier"; worth watching on the first recommendations after this ships.
- **Chips are per-slot, deterministic, and optional.** A fixed global set would ask about sleeves on footwear. `Domain/ItemFeedbackChipCatalog` is a lookup table — no LLM — mapping four shared chips (Love this piece / Not my style / Wrong colour on me / Uncomfortable fabric) plus per-slot complaints onto the two destinations; the two fit directions write *both* an `ItemRating.fit` and a note, since a fit complaint is genuinely both. A defect-only tap writes **no** rating, deliberately: a neutral rating would dilute the item's preference tally with a meaningless mid score. The row is collapsed by default under the existing swipe — this is an opt-in refinement, not a second form standing between the user and submitting.
- **The whole-look sentiment now fans out per-garment at `1/N`, so learning no longer depends on the user tapping anything.** `fetchFeedbackHistory` turns each combination-swipe row into one `OutfitDimensionRatedAttributes` per garment at `1.0 / items.count` (`OutfitDimensionRatedAttributes` gained `weight`, composed with decay by multiplication exactly as `RatedAttributes.weight` already was) — the same credit assignment a multi-garment stock swipe uses, for the same reason: one judgment about N garments is not N independent judgments. `patternDissatisfaction` stays `nil` on this path: a disliked outfit is not evidence the *pattern* was the problem, and inventing that signal would teach `patternAffinity` something the user never expressed.
- **`ratingSampleSize` now counts the feedback the app actually collects** (`normalizedRating != nil || swipeSentiment != nil`), which is what unlocks Style DNA from real usage and therefore lets the assistant answer taste questions at all.
- **The recommender finally hears combination and per-category taste.** `StylistBrain` gains: the 7 scoreable combination dimensions phrased as relationships between garments (`aestheticVibe`/`complexityScore` stay Insights-only — there's no reliable way to act on a learned "vibe" score for a candidate not yet built); the five expanded attributes; and per-slot lines emitted **only where a slot diverges from the flat map** by `slotDivergenceThreshold` *and* the divergence flips the verdict, capped at 12 and sorted by magnitude. Listing all seven slots across every dimension would multiply the block ~7x while mostly restating the flat lists; the divergence rule makes the prompt say "leans muted, but prefers bold footwear", which is the actual information. Because the section roughly doubled, the Tier-5 subordination line is restated once at its end — a longer, more specific-sounding preference list is exactly what tempts a model to let Tier 5 outrank Tier 2.
- **The free-text comment stopped being inert, through a call that already existed.** `CombinationChemistryInferenceService` already received the comment *and* the catalog with real ids; its schema now wraps the unchanged `CombinationMetadataSchema.objectSchema` in `{chemistry, item_notes}` (a wrapper, not extra properties, because that object is shared verbatim with stock-photo scene tagging where no owned-item ids exist). So "great outfit but the shirt is loose" lands as a note on that shirt at no extra call and no extra cost. Ids the model invents or that aren't in the shown combination are dropped, and notes are written `source: .inferred` so Closet shows them as a machine reading of the comment, one tap from correction — misattribution is this path's main failure mode and that visibility is the mitigation, not a claim the inference is perfect. **Deliberately narrowed from the plan:** the extraction records only garment *facts*, never taste opinions, even though a comment may contain both. A taste claim would move the global affinity maps on an LLM's reading of one sentence with no confirmation step; the chips already capture taste deterministically with the user's own finger on the button.

## Deferred (later phases)

Full knowledge-module extraction (separate Color Theory / Fabric Science / Dress Code / Silhouette / Footwear modules with individual applicability predicates and prompt-budget eviction), the validator's contextual (Tier B) and repair (Tier C) tiers, a named versioned Recommendation Rubric with per-dimension subscores, exemplar-based taste injection, and controlled vocabularies for the rich garment attributes are all real next steps but were not done in this pass — each touches either the live structured-output contract with `google/gemini-3.1-flash-lite` or the well-tested numeric scoring engine, and is better done incrementally with its own regression coverage rather than in one sweep. See the full architecture design for the target end-state; this file tracks only what's actually shipped.
